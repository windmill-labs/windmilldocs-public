# OpenID Connect (OIDC)

Use Windmill's OIDC provider to authenticate from scripts to cloud providers and other APIs.

OIDC is an [EE feature only](/pricing).

Windmill OpenID Connect (OIDC) allows your scripts to authenticate to other APIs (such as AWS, GCP, or your own API) without having to store sensitive, long-lived credentials.
Your Windmill scripts can generate short-lived ID tokens which are passed to a target API to authenticate and "prove" their identity. ID tokens contain subject and claim information specific to the script, flow or worker, allowing for fine-grained access control (e.g. allowing specific scripts to access AWS buckets).
This page documents how to generate Windmill tokens and the token format.

## Generating OIDC/JWT tokens

OIDC tokens are generated at runtime and are scoped to the script that generated them. Tokens can be generated with Windmill's SDKs or from the REST API directly.
Your token must be associated with an audience which identifies the intended recipient of the token. The audience is provided as a parameter when generating the token. If the audience is incorrect, the consumer will reject the token. (For AWS, this audience is sts.amazonaws.com. For your own APIs, you can specify an audience such as auth.yourcompany.com.)
If you are using a TypeScript or Python scripts, you can use the Windmill SDK to generate tokens. For other like REST or shell, you should use the REST api directly:

```
curl -s -X POST -H "Authorization: Bearer $WM_TOKEN" "$BASE_INTERNAL_URL/api/w/$WM_WORKSPACE/oidc/token/MY_AUDIENCE"
```

The default expiry time is 48 hours.
Set another one in seconds with the `expires_in` query parameter, change the default with the `OIDC_TOKEN_EXPIRY_SECS` environment variable, and cap what a job can request with `OIDC_TOKEN_MAX_EXPIRY_SECS`.
A token is only issued while the job is running and not being canceled: its `WM_TOKEN` cannot mint one afterwards.

### Generate the token

Tokens can be generated at runtime with Windmill's SDKs. For example, to generate an OIDC token with audience sts.amazonaws.com to assume an AWS role:

## Token payload reference

OIDC tokens generated by Windmill's OIDC provider are signed JSON web tokens (JWTs). The ID token is encoded by using RS256 and signed with a dedicated private key. The expiry time for the token is set for 48 hours.
The token includes standard claims:

- `aud`: Intended audience for the token. This field is set by the user when fetching the ID token and is the only customizable field.
- `iss`: The issuer of the token, your base_url set in in your i[nstance settings](../../advanced/18_instance_settings/index.mdx#base-url)
- `sub`: The subject claim is validated by your cloud provider. The subject is formatted as `{email}::{script_path}::{flow_path}::{workspace}`. For instance level, the sub claim is "instance". For SQS triggers and workspace level object storage, the sub claim is "`<workspace_id>`".- `exp`: The expiration time of the token.
- `iat`: The time the token was issued.
- `alg`: The algorithm used to sign the token.
- `kid`: The key ID used to sign the token.

The token also includes custom claims provided by Windmill. To see the full list of claims supported by Windmill's OIDC provider, see the `claims_supported` entries at `<base_url>/api/oidc/.well-known/openid-configuration`. Note that not all cloud providers support all claims.

- `job_id`: Job id
- `path`: Job's path (the script path for a script or a virtual path for a step part of a flow)
- `flow_path`: If job is part of a flow, contain the path of the flow
- `groups`: the groups the requester is part of
- `username`: the username the requester has in the given workspace
- `email`: the email of the requester
- `workspace`: workspace_id the job is executed in
- `fork_parent_workspace`: when the job runs in a [workspace fork](../../advanced/20_workspace_forks/index.mdx), the workspace_id of the parent workspace. This lets OIDC consumers such as Vault write policies scoped to the parent workspace that also apply to all its forks. The claim is omitted for non-fork workspaces, and workspace-level tokens (workspace object storage, SQS triggers) do not include it.
- `end_user_email`: the email of the end user when the job runs on behalf of a different user (e.g. via approval flows or operator impersonation)
- `job_kind`: the kind of job that requested the token, e.g. `script`, `preview`, `flow`, `flowscript` (an inline flow step), `appscript` or `aiagent`
- `deployed`, `latest`: whether the job runs deployed code, and its current version. See [Trust only deployed code](#trust-only-deployed-code).
- `version`: the script hash of a `script` job or the flow version id of a `flow` job, `null` for other kinds
- `digest`: the SHA-256 of the job's code, `null` for kinds other than `script`, `flow` and `flowscript`. See [Pin code with digests](#pin-code-with-digests).
- `root_job_id`, `root_path`, `root_job_kind`, `root_version`, `root_digest`: the same for the job at the top of the chain of parent jobs, e.g. the flow that ran this step, or the job itself when it has no parent. A flow restarted from a step is a new job, with a new `root_job_id`.
- `root_trigger_kind`, `root_trigger`: how the root job was started (e.g. `schedule`, `webhook`, `http`) and by what, `null` when none was recorded, e.g. for a run started through the API. See [what `root_trigger` holds](#what-root_trigger-holds).
- `tag`, `worker_group`: the job's [worker tag](../9_worker_groups/index.mdx) and the worker group of the worker running it. Windmill records them, the worker does not attest them: whoever can start a worker under a group name or deploy code with a tag sets them.
- `run_as_type`: what `email` names: `user`, `service_account`, `group` or `non_member` (a superadmin outside the workspace, a built-in identity or a removed user)
- `job_token_scopes`: the scopes of a [restricted job token](../59_user_tokens/index.mdx#restricted-job-tokens), e.g. `["oidc:write"]`, absent when the job token is unrestricted
- `jti`: a unique id per token, to refuse a token presented twice

### Trust only deployed code

`deployed` is `true` only when the job and every job above it in the chain run code at a path taken from a deployed version, or a published Hub script.
It is `false` for anything run from the script, flow or app editor, and for a deployed script called from a flow preview.
`latest` is `true` only when the token is `deployed` and every script and flow in the chain runs the version its path currently resolves to.
It is always `false` under an app.

`deployed` alone accepts every past version, which anyone who can run a script or flow can still run.
Require `latest` so that redeploying over a bad version revokes it, or pin `version` and `root_version`.
For example, to issue a credential only to the steps of one deployed flow, on a provider that checks custom claims (e.g. Vault's `bound_claims`), bind:

- `workspace` = `foobar`
- `path` matching `f/infra_ro/*` (in Vault, with `"bound_claims_type": "glob"` on the role)
- `root_path` = `f/infra_ro/agent`
- `deployed` = `true`
- `latest` = `true`

Both are computed each time a token is requested, and turn `false`, even during a run, when:

- `latest`: a script or flow of the chain is redeployed
- `deployed`: the job's script version is deleted, its script or flow is permanently deleted, or its user folder is renamed
- `deployed`: for the inline steps of a flow, the instance runs with `DISABLE_FLOW_SCRIPT`, or the flow was last deployed before flow nodes existed (redeploy it)

A preview declares its own path, so its token carries the `path` and `sub` of the item deployed there.
Windmill therefore only issues a token to a job that is not `deployed` when its user has [write access](../16_roles_and_permissions/index.mdx#permissions-and-access-control) to the script, flow or app at every path the preview declares (its own, and any path set on a flow step that points outside the flow): otherwise the request fails with a 403.
That includes deployed code that [runs as another user](../16_roles_and_permissions/index.mdx#run-on-behalf-of) when called from such a preview, and, unless the user is an admin, a job whose chain exceeds 100 parent jobs or leaves the workspace.
A preview with no path, or under the user's own `u/<username>/` folder, always gets one.

Providers that only match `sub` (e.g. AWS) cannot see `deployed`, `latest` or `version`, and `sub` is the same for a preview and for every version: such a role trusts everyone who can write or run the paths it names, so restrict both.

### Pin code with digests

`version` identifies code inside one instance only.
`digest` and `root_digest` are the lowercase hex SHA-256 of the [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) canonical JSON of the item, with `null` members left out, so a policy can accept only code reviewed in git.
Compute them with [`wmill digest`](../../advanced/3_cli/index.mdx#wmill-digest) from the root of a [`wmill sync`](../../advanced/11_git_sync/index.mdx) checkout:

```bash
wmill digest f/infra/agent__flow f/infra/tool.ts
# 762edbbcb8c0e84744206f8efa707f10945540e3a00cb454f0dbd31520b18ddd  f/infra/agent
# abf4646174c8d6984ea9f6d9c6746b61c3d95cd0cb91a4ca89b884b0f61600ae  f/infra/agent/a
# fcf85b60c3d9aef073e6911f417fdd19bedeb6d9e0f36b2589df07900997f29d  f/infra/tool
```

- a script: `{"content", "lock", "codebase", "modules"}`, where `modules` is `{"<relative path>": {"content", "lock"}}` for a multi-file script
- an inline flow step: `{"content", "lock"}`, listed as `<flow path>/<step id>`, the `path` of its `flowscript` job
- a flow: its `value`, as `flow.yaml` holds it once the `!inline` files are read back in

A digest covers code and lockfiles, not the language, the settings and metadata (tag, schema) or the scripts it imports.
Compare against a checkout pulled with `wmill sync pull` after the deployment's dependency jobs completed, not the files you pushed: those jobs write the lockfiles and fill in the default settings of a flow's loops and branches.

### What `root_trigger` holds

`root_trigger` depends on `root_trigger_kind`:

- `schedule`: the schedule's path, `null` for its success and recovery handlers
- `http`, `websocket`, `kafka`, `nats`, `mqtt`, `amqp`, `sqs`, `postgres`, `gcp`, `azure`: the trigger's path, not its route, topic or queue
- `email`: the email trigger's path, `null` for an email sent to a script's or flow's own address
- `app`: the app's path
- `asset`: the path of the script that produced the asset
- `nextcloud`, `google`, `github`: an external id supplied by whoever calls the run endpoint, as is the kind itself: do not trust them
- `webhook`: `null`

A job started by an [HTTP route](../../triggers/2_http_routing/index.mdx) runs as the identity configured on the route: `sub`, `email`, `username` and `groups` never describe the caller.


## Signing key

By default, Windmill signs OIDC tokens with a 2048-bit RSA key that it generates and stores in the database, with the `kid` `windmill`.
The same key signs the tokens Windmill presents to Vault, object storage, SQS and the AI proxy.

To keep the key out of the database, set `OIDC_SIGNING_KEY_FILE` on every server and worker to the path of the same PEM RSA private key (PKCS#1 or PKCS#8, 2048 to 4096 bits):

```bash
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out oidc-signing-key.pem
```

A file key's `kid` is its [RFC 7638](https://www.rfc-editor.org/rfc/rfc7638) thumbprint, so it changes with the key.
Verifiers that fetch `<base_url>/api/oidc/jwks` follow on their own, while one configured with a static copy of the key has to be updated at every change.

Switching from the database key to a file invalidates the tokens signed with the database key at once: it cannot stay published as `kid: windmill`.
Then delete it, so that a copy of the database or a backup can no longer sign tokens:

```sql
DELETE FROM global_settings WHERE name = 'rsa_keys';
```

### Rotate the key

The key file is re-read at every signature, and the JWKS also serves every `*.pem` file (private or public key) of the `OIDC_SIGNING_KEY_PUBLISH_DIR` directory, listed on every request.
With the current public key in that directory, a rotation needs no restart:

1. Add the new public key to the directory, and wait until every server and worker sees it (a mounted Kubernetes secret can take a minute or more) and verifiers that cache the JWKS have refetched it.
2. Write the new private key to the signing key file, atomically (write a temporary file without the `.pem` extension, then rename it).
3. Once the tokens signed with the old key have expired, delete its file from the directory. `OIDC_TOKEN_MAX_EXPIRY_SECS` bounds that wait.

## Use OIDC with AWS

### Create an identity provider with AWS for OIDC

1. Search for the `Identity Providers` tab in the console search or IAM.
2. Add provider
3. Select OpenID Connect
4. Provider Url: `<base_url>/api/oidc/`, audience: `sts.amazonaws.com`

### Create a role

1. IAM -> Roles -> Create Role
2. Web Identity
3. Pick provider created above, audience: `sts.amazonaws.com`
4. Pick the permission policy to attach to this role. You can create as many roles as needed so it's best to be specific.
5. fill the Trust policy:

```
{
  "Version": "2012-10-17",
  "Statement": [
      {
          "Effect": "Allow",
          "Action": "sts:AssumeRoleWithWebIdentity",
          "Principal": {
              "Federated": "arn:aws:iam::976079455550:oidc-provider/<base_url>/api/oidc/"
          },
          "Condition": {
              "StringEquals": {
                  "<base_url>/api/oidc/:aud": "sts.amazonaws.com",
                  "<base_url>/api/oidc/:email": "example@example.com",
                  ...
              }
          }
      }
  ]
}
```

Note that [AWS only supports conditions on the `aud`, `sub`, and `email` claims](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_iam-condition-keys.html#condition-keys-wif). You can use `StringLike` on the `sub` claim to limit by job, flow, or workspace:

```
"StringLike": {
  "<base_url>/api/oidc/:sub": "*::<workspace>",
  "<base_url>/api/oidc/:sub": "*::<script_path>::*::*",
  "<base_url>/api/oidc/:sub": "*::*::<flow_path>::*"
}
```

For instance level AWS OIDC for [instance object storage](../../advanced/18_instance_settings/index.mdx#instance-object-storage), the sub claim is "instance". For [workspace level object storage](../../core_concepts/38_object_storage_in_windmill/index.mdx#workspace-object-storage), and SQS oidc triggersthe sub claim is "&lt;workspace_id&gt;".

## Use OIDC with Hashicorp Vault

```
vault auth enable jwt

vault write auth/jwt/config \
  bound_issuer="<base_url>/api/oidc/" \
  oidc_discovery_url="<base_url>/api/oidc/"

vault write auth/jwt/role/myproject-production -<<EOF
{
  "role_type": "jwt",
  "bound_audiences": ["MY_AUDIENCE"],
  "bound_claims": { "email": "admin@windmill.dev"},
  "user_claim": "sub",
  "policies": ["myproject-production"],
  "ttl": "10m"
}
EOF

 vault policy write myproject-production - <<EOF
# Read-only permission on 'secret/data/production/*' path

path "secret/data/production/*" {
  capabilities = [ "read" ]
}
EOF
```
