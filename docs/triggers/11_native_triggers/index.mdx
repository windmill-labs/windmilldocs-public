# Native triggers

Native triggers allow external services to push events directly to Windmill and trigger [scripts](../../script_editor/index.mdx) and [flows](../../flows/1_flow_editor.mdx). Unlike [scheduled polls](../../flows/10_flow_trigger.mdx), native triggers receive real-time push notifications from the external service via webhooks, so your runnables execute as soon as events occur.

Currently supported services:

- [Nextcloud](#nextcloud-triggers) - file, folder, and calendar change events
- [Google](#google-triggers) - drive and calendar change events
- [GitHub](#github-triggers) - repository events such as pushes, pull requests, issues and releases

---

## How it works

Native triggers use [OAuth](../../advanced/27_setup_oauth/index.mdx) to authenticate with the external service. Each trigger registers a webhook or watch channel on the external service, which sends notifications to Windmill when events occur. Windmill then executes the configured script or flow with the event data.

Each trigger acts as one connected account of the service, its [connection](#connections): the webhook is registered under that account, and the trigger only sees what that account can access.

The general setup follows two steps:

1. **Configure the OAuth app** of the service in workspace settings (an admin does this once, unless the instance shares one)
2. **Create a trigger** on a script or flow, picking the account it acts as and configuring which events to watch

---

## Setup

### Workspace integration

A workspace admin configures the OAuth app of each service in **Workspace settings** > **Integrations** > **Native triggers**, by providing the [OAuth](../../advanced/27_setup_oauth/index.mdx) client ID and client secret.
The same page holds the [shared account](#share-an-account-with-the-workspace) of each service.

For Google, the OAuth scopes used are:
- `https://www.googleapis.com/auth/drive.readonly`
- `https://www.googleapis.com/auth/calendar.readonly`
- `https://www.googleapis.com/auth/calendar.events`

If you need additional scopes (e.g. write access), set up a separate resource with the desired scopes.

For GitHub, the OAuth scopes used are `repo` and `read:user`.

A superadmin can share the [instance-level](../../advanced/18_instance_settings/index.mdx) Google and GitHub OAuth apps.
A workspace that configures no OAuth app of its own then uses the instance's, without its credentials being exposed to workspace admins.

![Instance gworkspace settings](./instance_gworkspace.png "Instance-level gworkspace settings with shared credentials toggle and redirect URI")

For Nextcloud, you also need to provide the base URL of your Nextcloud instance.

### Connections

A connection is a connected account of the service, stored as a [resource](../../core_concepts/3_resources_and_types/index.mdx) and its OAuth token [variable](../../core_concepts/2_variables_and_secrets/index.mdx) in the workspace.
Its token is refreshed automatically, and scripts can use the resource to call the service API as the same account as the trigger.

Members whose [workspace role](../../core_concepts/16_roles_and_permissions/index.mdx#workspace-roles) can both write code and manage triggers connect their own account in the trigger editor, with **Connect a GitHub account** (or Google, Nextcloud).
Using a connection requires read access to its token variable: to let others use an account you connected, save it in a [folder](../../core_concepts/8_groups_and_folders/index.mdx) they can read or share its variable with them.
Disconnecting an account deletes every trigger that uses it, including other members'.

#### Share an account with the workspace

An admin can pick one connection per service as the **Shared account**, in the service's card in workspace settings.
Members can then create and edit triggers that act as it without being able to read its token.

Only Nextcloud admins can register webhooks, so Nextcloud triggers need a Nextcloud admin account: share one with the workspace so every member can create them.

### Create a trigger

Once the service has an OAuth app, from the [workspace integration](#workspace-integration) or the instance:

1. In the script or flow's **Triggers** tab, click **Add trigger** and pick the service
2. Under **GitHub account** (or Google, Nextcloud), pick the [connection](#connections) the trigger acts as
3. Configure the service-specific options (see sections below)
4. Save the trigger

You can also click **New trigger** on the service's page in the sidebar, then select the script or flow.

## Nextcloud triggers

First of all make sure you set up the [workspace integration](#workspace-integration) for Nextcloud.

Nextcloud native triggers watch for file, folder, and calendar changes on a [Nextcloud](https://nextcloud.com/) instance and trigger a script or flow when events occur.

### Prerequisites

- Nextcloud 33 or later
- The [Windmill integration app](https://apps.nextcloud.com/apps/integration_windmill) installed on your Nextcloud instance
- [Pretty URLs](https://docs.nextcloud.com/server/latest/admin_manual/installation/source_installation.html#pretty-urls) enabled on your Nextcloud instance

### Configuration

When creating a Nextcloud trigger, pick a script or flow (or use **Create from template**), then configure:

- **Event** - select the event type to listen for. Available events include:
  - Calendar events: object created, moved, trashed, restored, or changed in a Nextcloud calendar
  - File/folder events: node created, changed, or written

![Nextcloud trigger configuration](./nextcloud_trigger.png "Nextcloud trigger creation with event type selection")

### Event payload

Nextcloud sends the full event data to your script. The payload includes the authenticated user, a timestamp, and the event details:

```typescript
export async function main(
  authentication: {
    owner: RT.Nextcloud;
    trigger: RT.Nextcloud;
  },
  user: {
    uid: string;
    displayName: string;
  },
  time: number,
  event: any
) {
  // event contains the Nextcloud event details (file, folder, or calendar object)
}
```

## Google triggers

First of all make sure the Google OAuth app is available, from the [workspace integration](#workspace-integration) or the instance.

Google native triggers watch for changes in [Google Drive](https://drive.google.com/) or [Google Calendar](https://calendar.google.com/) and trigger a script or flow when events occur.

### Prerequisites

- A Google Cloud project with the relevant API enabled ([Drive API](https://developers.google.com/drive/api), [Calendar API](https://developers.google.com/calendar/api), or both)
- [OAuth 2.0](https://console.cloud.google.com/apis/credentials) credentials (client ID and client secret) configured with the appropriate scopes

Neither is needed when the workspace uses the instance's shared Google OAuth app.

### Configuration

When creating a Google trigger, pick a script or flow (or use **Create from template**), then configure:

- **Trigger Type** - choose between **Drive** and **Calendar**
- **Watch Mode** (Drive only) - choose between:
  - **Specific file** - watch a single file or folder from My Drive, Shared with me, or Shared drives
  - **All changes** - watch all changes across your Google Drive (fires whenever any file is created, modified, or deleted)
- **Calendar** (Calendar only) - select a calendar from your Google account to watch for event changes

![Google trigger configuration](./google_trigger.png "Google trigger creation with trigger type and watch mode selection")

Both use push notifications via Google watch channels. Windmill automatically renews channels before they expire. The expiration period differs by service: 24 hours for Drive, 7 days for Calendar.

### Event payload

Google push notifications only contain metadata about the change, not the full event details. To get the actual content of the change, use the `gworkspace` [resource](../../core_concepts/3_resources_and_types/index.mdx) of the trigger's [connection](#connections) to query the Google API.

```typescript
type GoogleTriggerPayload = {
  channel_id: string;
  resource_id: string;
  resource_state: string; // "sync" | "exists" | "not_exists" | "update"
  resource_uri: string;
  message_number: string;
  channel_expiration: string;
  channel_token: string; // custom token set when creating the watch
  changed: string; // Drive-only: comma-separated list (e.g. "content,properties,permissions")
};

export async function main(payload: GoogleTriggerPayload) {
  // Use the gworkspace resource to query the Google API for full details
}
```

Use the [Google native trigger template script](https://hub.windmill.dev/scripts/gworkspace/22221/google-native-trigger-template-script-gworkspace) (also available from the UI when creating a trigger) as a starting point.

## GitHub triggers

First of all make sure the GitHub OAuth app is available, from the [workspace integration](#workspace-integration) or the instance.

GitHub native triggers register a webhook on a [GitHub](https://github.com/) repository and trigger a script or flow when the selected events occur.
Registering a webhook requires admin rights on the repository for the trigger's account.

### Configuration

When creating a GitHub trigger, pick a script or flow, then configure:

- **Repository** - a repository the trigger's account can access
- **Events** - the repository events to receive (push, pull request, issues, release, workflow run and more)

### Event payload

The script receives the event name from the `X-GitHub-Event` header, the delivery ID, and the [webhook payload](https://docs.github.com/en/webhooks/webhook-events-and-payloads) sent by GitHub:

```typescript
export async function main(
  event: string, // e.g. "push", "pull_request"
  delivery_id: string,
  payload: any
) {
  // payload is the GitHub webhook payload for this event
}
```
