# Backend runnables

Backend runnables are scripts that run on Windmill workers and are called from your [frontend code](../3_frontend/index.mdx) via the `wmill.ts` module. They live in the `backend/` folder of your full-code app.

## File structure

Each runnable consists of up to three files in the `backend/` directory:

```
backend/
├── get_users.ts            # Code file (required)
├── get_users.yaml          # Config file (optional)
├── get_users.lock          # Lock file (auto-generated)
├── run_query.pg.sql        # SQL runnable (language from extension)
└── run_query.lock
```

The runnable ID is derived from the filename: `get_users.ts` → runnable ID `get_users`.

## Code-only runnables (auto-detect)

The simplest way to define a runnable is to place a code file in `backend/`. The language is detected from the file extension and the runnable is treated as an inline script:

```
backend/get_users.ts        → TypeScript (Bun) inline script, ID: "get_users"
backend/fetch_data.py       → Python inline script, ID: "fetch_data"
backend/query.pg.sql        → PostgreSQL inline script, ID: "query"
```

No `.yaml` file is needed for code-only runnables.

## Explicit YAML config

For more control, create a `.yaml` file alongside the code file:

### Inline scripts

```yaml
# backend/get_users.yaml
type: inline
fields:
  workspace_id:
    type: static
    value: "my_workspace"
```

The code is in the sibling file (`get_users.ts`, `get_users.py`, etc.).

### Path-based runnables

Reference an existing workspace [script](../../script_editor/index.mdx) or [flow](../../flows/1_flow_editor.mdx):

```yaml
# backend/process_order.yaml
type: script
path: f/production/process_order
```

```yaml
# backend/onboarding.yaml
type: flow
path: f/flows/user_onboarding
```

```yaml
# backend/send_email.yaml
type: hubscript
path: hub/123/sendgrid/send_email
```

Hub flows from the [Windmill Hub](https://hub.windmill.dev) can also be selected as backend runnables from the flow picker in the UI.

### Static fields

You can pre-fill runnable inputs with static values so the frontend doesn't need to pass them:

```yaml
# backend/get_users.yaml
type: inline
fields:
  limit:
    type: static
    value: 100
  workspace:
    type: static
    value: "production"
```

Field types:

| Type | Description |
|------|-------------|
| `static` | A fixed value, set in the YAML |
| `ctx` | A value from the app context (e.g., user email), see [context fields](#context-fields) |
| `user` | Provided by the frontend at call time |

### Context fields

A context field is filled by the server from the viewer's session, so the frontend cannot set or override it.
Use one whenever a runnable needs to know who is viewing the app, for example to filter rows per viewer:

```yaml
# backend/my_orders.yaml
type: inline
fields:
  username:
    ctx: username
```

```sql
-- backend/my_orders.duckdb.sql
-- $username (text)
ATTACH 'datatable' AS dt;
SELECT * FROM dt.orders WHERE owner = $username;
```

The available properties are `username`, `email` and `groups` of the viewer, `workspace`, and `author` (the email the app runs on behalf of).
The viewer properties are `null` for a viewer who is not logged in on a [public app](../7_deployment/index.mdx#public-and-guest-apps).

An argument left as a frontend input takes whatever the browser sends, so a viewer filter declared that way lets any viewer read someone else's rows.
[`wmill app lint`](../../advanced/3_cli/app.md#lint-an-app) and the Inputs tab of the [app editor](../6_ui_editor/index.mdx) warn when an inline SQL runnable has an argument named `username`, `email` or `groups` that is neither a context nor a static field.
The check matches on those names only: it does not catch a filter named otherwise (`user_id`) or one in a non-SQL runnable.

## Read data as the viewer

A backend runnable reads data as the identity the app runs as, the publisher in publisher [execution mode](../7_deployment/index.mdx), the same for every viewer.
An inline runnable can instead read data as the logged-in person using the app, so that what it returns differs per viewer:

- A [data table](../4_data_tables/index.mdx) connection that names no role holds the viewer's [roles](../../core_concepts/11_persistent_storage/data_tables.mdx#connections-that-name-no-role) instead of the app's, so [row-level security](../../core_concepts/11_persistent_storage/data_tables.mdx#row-level-security-per-viewer) answers per viewer.
- [Object storage advanced permission rules](../../core_concepts/38_object_storage_in_windmill/index.mdx#resources-permissions) are checked against the viewer, so per-user paths such as `u/{username}/**` resolve to the viewer's.

Resources, variables and everything else the runnable reaches stay the app's.
A viewer who is not logged in, on a [public app](../../apps/8_public_apps.mdx), is refused.
Both data table roles and object storage permission rules are [Enterprise Edition](/pricing) features, and data table roles are only available on self-hosted instances.

It applies to inline runnables only: a path-based runnable is someone else's script, and always reads as the app.
In the app editor, turn on Read data as the viewer from the button in the inline runnable's toolbar, shown once its code reads a data table or object storage.
With the [CLI](../5_cli_workflow/index.mdx), set it in the runnable's YAML file:

```yaml
# backend/get_orders.yaml
type: inline
viewer_data_access: true
```

The [AI chat](../../core_concepts/22_ai_generation/index.mdx) can also turn it on when it creates or edits a runnable.

## Lock files

Lock files (`.lock`) pin dependency versions for reproducible builds. Generate them with:

```bash
wmill generate-metadata
```

This creates a `.lock` file for each runnable that has dependencies (TypeScript, Python, PHP).

## Example

A TypeScript runnable that queries a database:

```typescript
// backend/get_users.ts
import { Client } from "pg";

export async function main(limit: number = 10) {
  const client = new Client(process.env.DATABASE_URL);
  await client.connect();
  const result = await client.query("SELECT * FROM users LIMIT $1", [limit]);
  await client.end();
  return result.rows;
}
```

Called from the frontend:

```typescript
import { backend } from "./wmill.ts";

const users = await backend.get_users({ limit: 20 });
```
