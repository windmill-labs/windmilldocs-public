## Windmill vs Kestra at a glance

Windmill is an open-source workflow engine and developer platform to build and orchestrate internal software: [scripts](../script_editor/index.mdx), [workflows](../flows/1_flow_editor.mdx), [data pipelines](../core_concepts/27_data_pipelines/index.mdx), [AI agents](../core_concepts/54_ai_agents/index.mdx) and internal apps.
It is made for engineers who want full code flexibility and a [local development](../advanced/4_local_development/index.mdx) experience, both to build internal software and to manage the underlying infrastructure.

Kestra is an open-source workflow orchestrator for data, AI and infrastructure pipelines.
Flows are declarative YAML, backed by a catalog of 2,600+ plugins.
It suits teams that prefer configuration over imperative code and already think in YAML DAGs (Airflow, dbt, Kubernetes).

Both platforms orchestrate workflows.
The difference is what else you can build on the same runtime.

| What you can build | Windmill | Kestra |
| --- | --- | --- |
| [Workflows](../flows/1_flow_editor.mdx): chain scripts into flows with branching, retries and approval steps | Yes | Yes |
| [Data pipelines](../core_concepts/27_data_pipelines/index.mdx): ETL, syncs and scheduled data jobs with parallel branches | Yes | Yes |
| [Scripts](../script_editor/index.mdx): standalone functions exposed as APIs, webhooks or cron jobs without a wrapping workflow | Yes | No |
| [AI agent workflows](../core_concepts/54_ai_agents/index.mdx): agents that call tools, branch on outputs and run as workflows | Yes | Yes |
| [AI sandboxes](../core_concepts/68_ai_sandbox/index.mdx) and [volumes](../core_concepts/67_volumes/index.mdx): isolated environments with persistent volumes for running agents | Yes | No |
| [Low-code internal apps](../apps/0_app_editor/index.mdx): drag-and-drop dashboards and admin tools with built-in components | Yes | Partial (Enterprise Apps, defined in YAML) |
| [Full-code internal apps](../full_code_apps/index.mdx): custom dashboards and admin tools built in React or Svelte | Yes | No |
| [Scheduled tasks](../core_concepts/1_scheduling/index.mdx): cron jobs with retries, error handling and alerting | Yes | Yes |

Windmill is built to centralize and orchestrate internal software in one place.
Scripts, workflows, data pipelines, full-code apps, AI agents and operator UIs run on a single runtime, with shared resources, auth and observability.
Kestra focuses on workflow orchestration, so you bring your own stack for dashboards, internal apps and agent front-ends.

## Who each platform is built for

Windmill is built for developer-led teams where engineers own the platform end to end: code, Git, local development, workspace forks, code review, CI/CD, AI coding tools and infrastructure as code.
Non-developers consume what engineers build through [auto-generated UIs](../core_concepts/6_auto_generated_uis/index.mdx), custom apps and run-only [workspace roles](../core_concepts/16_roles_and_permissions/index.mdx#workspace-roles).
Reading or editing the flow logic itself still requires comfort with code.

Kestra is designed for teams that prefer declarative YAML over imperative code.
Data, ops and SRE engineers already comfortable with config files (Kubernetes manifests, dbt configs, Airflow DAGs) onboard faster than they would on a code-first platform.
Anyone comfortable reading YAML can inspect flows.
Meaningful edits still require understanding plugin task types, Pebble templating and trigger configs, which is its own technical skill.

Non-technical users can only partially author workflows on Windmill: it has a visual flow editor and auto-generated UIs, but authoring steps still involves writing code.
Kestra's declarative YAML is a better fit for teams already comfortable with config files.
Neither platform makes non-technical authoring frictionless.

## Open source

Both Windmill and [Kestra](https://github.com/kestra-io/kestra) have an open-source core that can be self-hosted, with Enterprise features sold separately. They both offer an easy installation process through [Docker](https://www.docker.com/), with pre-populated tutorial flows to help users get started.

Windmill provides and integrates into its platform a [public community Hub](https://hub.windmill.dev/) where users share useful and proven scripts, flows, and applications.

### Licenses

Windmill's open-source core is AGPLv3, which requires source availability for network-exposed modifications.
Kestra's open-source core is Apache 2.0, which is more permissive if you plan to modify and redistribute.
Both are free to self-host for unmodified use, and both offer a managed cloud.
If the license permissiveness of the core is a hard constraint, Kestra is ahead on this point.

## Language support and dependencies

Kestra provides [native support](https://kestra.io/docs/scripts) for Python, R, Node.js, Julia, Ruby, Shell, and PowerShell scripts. Additional language support is available through Docker containers. While this offers flexibility, there are some key differences in how dependencies are handled:

- In Kestra, dependency caching and pre-installed [dependencies](https://kestra.io/docs/scripts/installing-dependencies) need to be managed manually by the user
- Windmill automatically handles [dependency](../advanced/6_imports/index.mdx) installation and caching, allowing developers to focus on writing code
- Windmill supports [TypeScript](../getting_started/0_scripts_quickstart/1_typescript_quickstart/index.mdx), [Python](../getting_started/0_scripts_quickstart/2_python_quickstart/index.mdx), [Go](../getting_started/0_scripts_quickstart/3_go_quickstart/index.mdx), [Bash](../getting_started/0_scripts_quickstart/4_bash_quickstart/index.mdx), [SQL](../getting_started/0_scripts_quickstart/5_sql_quickstart/index.mdx) and more [languages](../getting_started/0_scripts_quickstart/index.mdx) natively

Windmill runs TypeScript (Deno, Bun, Node.js), Python, Go, Bash, SQL, PowerShell, PHP, Rust and more (20+ languages in total).
Any npm, PyPI, Go, Maven or Cargo package is a first-class import with automatic dependency resolution and a per-script lockfile, and relative imports work across Python and TypeScript scripts in the same workspace.

Kestra runs its script languages through the `io.kestra.plugin.scripts.*` plugins.
Each runs inside a Docker container with a configurable image, so packages install via pip, npm, gem and similar tools during the task.

## Architecture and development experience

Both platforms share a similar architecture centered around a queue-based system for event-driven orchestration of tasks and flows. However, there are several key differences in the development experience.

### Configuration and workflow building

Kestra:

- Uses YAML-first configuration for workflows where scripts are referenced as files (recently introduced a no-code interface for basic workflow creation)
- Requires passing arguments between steps through file I/O
- Passes simple arguments as environment variables

Kestra takes a code-only approach. Workflow creation is done through a YAML file. Each task is a value in the YAML, and most of your tasks will be separate files that need to be referenced in the flow (e.g. Python code can type `io.kestra.core.tasks.scripts.Python`, `io.kestra.core.tasks.python.Commands`, `io.kestra.core.tasks.python.Script`).

![Kestra flow example](../assets/compared_to/flow_kestra.webp 'Kestra flow example')

Windmill:

- Provides a UI for workflow configuration and step advanced settings
- Offers a visual [Flow Editor](../flows/1_flow_editor.mdx)
- Allows direct passing of arguments between steps
- Supports both UI-based and code-based workflow creation

In Windmill, a step is simply a script in a language—nothing more. From the flow editor, you can select an existing script from your workspace or the Hub, or just write it directly in the integrated code editor. Each step can either be forked or saved as a separate script in your workspace.

![Windmill flow example](../assets/compared_to/flow_windmill_kestra.webp 'Windmill flow example')

Windmill parses the function signature of each script to generate its input UI, JSON schema and argument types.
Arguments pass between flow steps as direct return values, with no templating.
Besides the visual flow editor, you can define a workflow programmatically in Python or TypeScript with [workflows as code](../core_concepts/31_workflows_as_code/index.mdx), using native try/catch, parallel branches and the language's own control flow.

In Kestra, scripts in Python, Node.js, R, Shell and other languages can be saved as <a href="https://kestra.io/docs/concepts/namespace-files" rel="nofollow">namespace files</a>, but a script can't run on its own.
Every execution happens as a task inside a YAML flow, which defines inputs, outputs, dependencies and triggers.
There is no standalone script primitive with its own UI or API endpoint.

### Developer tools

Windmill is designed to integrate seamlessly with your existing tool stack and processes, with specific support for:

- [Local development support](../advanced/4_local_development/index.mdx)
- [Windmill CLI](../advanced/3_cli/index.mdx)
- [Git sync](../advanced/11_git_sync/index.mdx) for version control
- [VS Code extension](../cli_local_dev/1_vscode-extension/index.mdx)
- Built-in code editor with [AI assistance](../core_concepts/22_ai_generation/index.mdx) for autocomplete and code generation

Although Kestra offers an alternative for some of these features ([Version control with Git](https://kestra.io/docs/version-control-cicd/git), [Server CLI](https://kestra.io/docs/server-cli)), it does not allow for as seamless an integration with your existing tools.

With Windmill, you run scripts locally with the CLI and keep native language tooling (LSP, type-checking, linting), the VS Code extension and AI coding tools such as Claude Code and Codex.
Kestra provides a YAML schema with validation in its VS Code and JetBrains plugins, and a local server for running flows before deploy.

### Git and CI

In Windmill, scripts, flows, apps, resources, variables, secrets, schedules, folders, groups and permissions are all files in Git, deployed with the [CLI](../advanced/3_cli/index.mdx) and [Git sync](../advanced/11_git_sync/index.mdx) (see [infrastructure as code](../core_concepts/57_infrastructure_as_code/index.mdx)).
Internal tooling runs like application code: pull requests, reviews, rollbacks and CI/CD.

In Kestra, the open-source `SyncFlows` and `SyncNamespaceFiles` <a href="https://kestra.io/docs/version-control-cicd/git" rel="nofollow">Git tasks</a> and the <a href="https://kestra.io/docs/kestra-cli/kestractl" rel="nofollow">`kestractl` CLI</a> deploy flows and namespace files from a repository; syncing apps, blueprints, unit tests and dashboards is Enterprise.
Managing users, groups, roles and service accounts with `kestractl` is also Enterprise.
In open source, users and tenant settings live in the UI or behind the API.

## Data, resources and secrets

Windmill has [data tables](../core_concepts/11_persistent_storage/data_tables.mdx) with SQL queries, versioning and a browse and edit UI.
[Resources](../core_concepts/3_resources_and_types/index.mdx) (typed JSON for credentials, connection info and configs) and [variables](../core_concepts/2_variables_and_secrets/index.mdx) (individual secrets) are reusable across scripts, flows and apps.
They are encrypted at rest, scoped with folders and groups for access control, and versioned in Git.
[External secret backends](../core_concepts/2_variables_and_secrets/index.mdx#secret-storage-backends) such as Vault and AWS Secrets Manager are available on [Enterprise Edition](/pricing).

In Kestra, S3 access goes through the `io.kestra.plugin.aws.s3.*` plugin.
Per-task input and output files and a built-in KV store cover smaller values, and there is no dedicated data tables primitive.
The open-source edition ships <a href="https://kestra.io/docs/concepts/secret" rel="nofollow">basic secrets</a> as base64-encoded environment variables.
The UI secret manager, namespace- and tenant-scoped secrets, and external backends (Vault, AWS Secrets Manager) are Kestra Enterprise features.

## Integrations

### Connecting to external systems

In Windmill, any npm, PyPI, Go or Maven package is a first-class import with automatic per-script dependency resolution and lockfiles.
There is no plugin layer in between: you call the vendor's own SDK, with type inference and auto-completion in the editor.
50+ pre-built [resource types](../integrations/0_integrations_on_windmill.mdx) cover common databases (Postgres, Snowflake, BigQuery), SaaS (Slack, Stripe, GitHub, Notion, OpenAI) and infrastructure (S3, Redis, Kafka).
You paste an API key into a typed form, and the resource is shared across scripts, flows and apps, encrypted at rest.
The community [Hub](https://hub.windmill.dev/) has reusable scripts and flows for common tasks.

Kestra has a curated <a href="https://kestra.io/plugins" rel="nofollow">catalog of 2,600+ plugins</a>, with official connectors for Snowflake, BigQuery, dbt, Airbyte, Salesforce, Databricks and most common data-stack tools.
Each plugin bundles tasks, triggers and connection types that you reference by their fully qualified name in the flow YAML, with configuration that lives in Git alongside the flow.
Internally a task can wrap SQL, Python, shell or an API call; from the flow definition's perspective the surface is uniform YAML.

Windmill does not have a curated plugin catalog the size of Kestra's.
The trade-off is that in Windmill the package ecosystems themselves act as the catalog.
For mainstream data-pipeline tools that Kestra has official plugins for, Kestra is often easier to get started with.

### Receiving events

Windmill has native [triggers](../triggers/index.mdx) for HTTP, cron, Kafka, NATS, Postgres CDC, SQS, MQTT, SMTP and WebSocket.
Each trigger is configured in the UI: set the topic, subject or path, attach it to a script or flow, and Windmill handles the connection, replay and consumer-group state.
Every script also gets an HTTP endpoint and a [webhook](../core_concepts/4_webhooks/index.mdx) URL, so most receive paths need no glue code.
[Kafka](../triggers/5_kafka_triggers/index.mdx), [NATS](../triggers/6_nats_triggers/index.mdx) and [SQS](../triggers/7_sqs_triggers/index.mdx) triggers are self-hosted Enterprise features, and [Postgres](../triggers/4_postgres_triggers/index.mdx) and [MQTT](../triggers/8_mqtt_triggers/index.mdx) triggers are not available on Windmill Cloud.

Kestra has six core <a href="https://kestra.io/docs/workflow-components/triggers" rel="nofollow">trigger</a> types: Schedule (cron), Flow (run on another flow's completion), Webhook, Polling (check an external system on a cadence), Realtime (react to events with millisecond latency) and MCP Tool (expose a flow as a tool on a Kestra MCP server).
Plugin-based triggers extend the same model to Kafka, AMQP, JMS, MQTT and S3 events.

### Extending the platform

In Windmill, a new integration is a script with a new import: save and run, with no restart and no image rebuild.
This works the same in the web editor, the [CLI](../advanced/3_cli/index.mdx) and [Git sync](../advanced/11_git_sync/index.mdx).
Custom logic can be exposed as a typed script or packaged as a [resource type](../core_concepts/3_resources_and_types/index.mdx) for shared use.

Kestra has three options.
You can write a Java plugin against the Kestra SDK and ship it as a JAR alongside the worker.
You can drop to an inline Python, Node or shell script inside a flow for one-off logic.
Or you can save code as namespace files and call them from any flow in that namespace, the closest analogue to shared scripts.

## Migration and lock-in

Both platforms solve workflow orchestration with a queue-based, event-driven architecture, so the mental model transfers.
There is no automated converter from Kestra YAML to Windmill today.
Migration is a manual rewrite where each Kestra task becomes a Windmill script or flow step.
Most ported workflows end up shorter because Windmill passes arguments directly between steps and auto-generates input UIs.
Workflows that rely on specific Kestra plugins for exotic systems may require replacing those plugins with equivalent SDK calls in code.

### Getting in

In Windmill, you paste a function body into the [script editor](../script_editor/index.mdx), and Windmill infers the arguments, generates a UI and handles dependencies.
There is no YAML to learn.
Triggers, schedules, variables and apps migrate one by one.

In Kestra, if you already think in YAML DAGs (Airflow), the mental model transfers.
Each task becomes a plugin reference, with scripts inline or as files.

### Getting out

Windmill step logic is standard TypeScript, Python, Go, Bash or SQL that runs anywhere.
The CLI exports the full workspace as plain files.
What you lose when leaving Windmill is the runtime, not the step code.

Leaving Kestra depends on what your flows use.
Inline Python, Node or Shell scripts port cleanly, since the code body is standard.
Ecosystem plugins (`io.kestra.plugin.snowflake.*`, `stripe.*`, etc.) need rewriting against the vendor's SDK.
Built-in flow primitives (subflows, retries, conditionals) and Pebble templating (`{{ inputs.x }}`) also need reimplementing on the new platform.

However, there are a few features where they stand out from each other.

## Performance

Windmill's architecture allows running each task on the current fleet of worker
(which you can auto-scale automatically) and hence do not suffer from cold start.
Isolation and creating dedicated dependency environment is the secret sauce that makes Windmill
the fastest execution runtime for scripts (10ms cold start).

Windmill can run 26M tasks a month on a single worker costing 5$. Kestra does not provide figures on its average runtime and performance.

Also, Windmill has a [transparent API](https://app.windmill.dev/openapi.html#/), on which you could imagine launching 1m simulateously by API.

We have conducted [benchmarks](../misc/3_benchmarks/index.mdx) to measure our performance against our competitors.

In normal mode, Windmill is slightly faster than Kestra, while in [dedicated worker](../core_concepts/25_dedicated_workers/index.mdx) mode, Windmill is 3x faster.
For heavy-duty tasks that run for minutes, per-task overhead is a rounding error and the gap disappears.

Kestra is queue-based and horizontally scalable, with per-task overhead from JVM startup, plugin loading and state persistence.
That overhead is negligible for multi-minute tasks.
Windmill is faster for short, high-volume workloads like webhooks, alerts and small scripts, while Kestra is a good fit for long-running data tasks where per-task overhead doesn't matter.
See the [Kestra benchmark](../misc/3_benchmarks/competitors/kestra/index.mdx) for the setup and results.

## Conclusion

Windmill and Kestra solve orchestration with two different grammars.
Kestra models a workflow as a declarative YAML flow where every task is a plugin reference.
Windmill models a workflow as a graph of real scripts where each script is also a standalone primitive with its own UI, API endpoint and scheduler.

Kestra can be a good fit if your team already thinks in YAML DAGs, your workload is mainstream data orchestration that its plugin catalog already covers, and Apache 2.0 licensing of the core matters for redistribution.
The switching cost is asymmetric: Windmill step logic is standard code that runs anywhere after you leave, while Kestra flows built on ecosystem plugins and Pebble templating have to be rewritten on any other platform.

Kestra offers a solid foundation for workflow orchestration with its extensive plugin system. We believe that Windmill is a more intuitive solution for developers: the user doesn't need to "learn" a new framework but simply write code in the language they already know, using the [tools](#developer-tools) they are already familiar with (VS Code, GitHub, etc.). Dependencies are automatically handled and all settings are in an intuitive UI, not in a YAML file that only a few developers in your organization are familiar with.

The choice between the two may come down to specific needs: if you're looking for a pure workflow orchestration tool with extensive plugins, Kestra might be sufficient. However, if you need a more complete platform that includes UI building, automated dependency management, and intuitive development experience, Windmill would be the better choice.

If you're deciding between the two, the fastest way to judge is to spend an afternoon in each.
